# 顧客フォロー管理（CRM）— 全テナント標準機能

「今、誰にフォローすべきかが分かる」ためのオーナー向け顧客管理。
単なる台帳ではなく、**今月の誕生日・今週の予約・フォロー候補・休眠客**を自動抽出する。

## 使い方（オーナー向け）

- 入口：**オーナーポータル** `owner.html?s=サロンID&k=設定キー` の「今日」「顧客」タブ
  （旧 `crm.html` リンクは自動でポータルへ転送される）
- できること：顧客の登録・検索・編集、来店の記録（1タップで最終来店＝今日・回数＋1）、
  フォロー基準日数の変更、論理削除
- 誕生日は**月日だけでも登録可**。生年・最終来店日・次回予約日・メモはすべて任意
- 月が変わって最初に開いたとき、当月誕生日の人数を1回だけ控えめに通知（端末内で記憶）

## 判定ルール（Worker側に集約）

```
予約あり     = 次回予約日が「今日」以降（過去日の消し忘れは予約なし扱い）
経過日数     = 今日 − 最終来店日（「今日」はオーナー端末の日付を使用）
フォロー候補 = 経過 >= followDays(既定60) かつ 予約なし かつ 経過 < dormantDays
休眠客       = 経過 >= dormantDays(既定120) かつ 予約なし（候補とは重複しない）
「今週」     = 今日から7日以内（暦週ではない）
```

基準日数はテナント別に `tenant_settings`（`crm.followDays` / `crm.dormantDays`）で変更可能。

## 技術構成

- **API**：Worker `POST /crm`（action: dashboard / list / get / upsert / visit / delete / settings）
- **認証**：テナント別の設定キー（setup_token）。認証済みテナントの `id` を
  すべてのSQLの `WHERE tenant_id` に使う＝**リクエストから他テナントを指す構文が存在しない**
- **テーブル**：`customers`（論理削除・schema.sql参照）＋ `tenant_settings`（汎用KV）
- **自動マイグレーション**：テーブルは初回アクセス時にWorkerが自動作成
  （`CREATE TABLE IF NOT EXISTS`）。**新規サロン・新規D1でも手動SQL不要**

## プライバシー・安全

- お客様向けAI（受付・カウンセラー・ファクトリー）のコード経路は customers を一切参照しない。
  **顧客情報がAIプロンプトに載る経路が存在しない**（テストで実証済み）
- 顧客情報へのアクセスは管理リンク経由のみ。削除は論理削除（deleted_at）
- 実顧客情報を扱うため、**管理リンクは合鍵として扱うこと**
  （お客様に見せない・SNSに貼らない。漏れた場合は販売者が管理APIの `rotate` でキー再発行）
- 本格ログイン認証はM4（SaaS化フェーズ）で置き換え予定

## 将来拡張のフック

- 判定・抽出がすべて `/crm` APIに集約されているため、
  誕生日LINE文面のAI生成／休眠フォロー文面生成は「対象リスト＋既存 `callAI`」で実装できる
- 予約API連携は `next_reservation_date` を書き込むだけ（出所を問わない設計）。
  連携時は `source` 列の追加を推奨
- 来店履歴・施術履歴は `visits` テーブル追加で `visit_count` を自動集計へ移行
  （docs/03 のER設計と整合。現在の手動値は初期値として引き継ぐ）
